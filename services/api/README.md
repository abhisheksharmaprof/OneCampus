# CampusOne API

Django REST Framework backend for the CampusOne school CRM.

## Local setup

```bash
cd services/api
cp .env.example .env
uv sync --all-groups
uv run python manage.py migrate
uv run python manage.py runserver 0.0.0.0:8000
```

The checked-in `.env.example` is safe to share. The local `.env` is ignored by Git. It currently enables SQLite and eager Celery only so the project can boot before Railway credentials are entered.

## Replace Railway credentials

Open `services/api/.env` and replace:

```env
DJANGO_SECRET_KEY=<long-random-production-secret>
DJANGO_ALLOWED_HOSTS=<your-api-domain>.up.railway.app
CORS_ALLOWED_ORIGINS=https://<your-admin-web-domain>
CSRF_TRUSTED_ORIGINS=https://<your-admin-web-domain>
DATABASE_URL=${{Postgres.DATABASE_URL}}
DJANGO_USE_SQLITE=false
DATABASE_SSL_REQUIRE=true
REDIS_URL=${{Redis.REDIS_URL}}
CELERY_TASK_ALWAYS_EAGER=false
```

For Railway, set these as service variables rather than uploading the local `.env`. Railway reference-variable syntax such as `${{Postgres.DATABASE_URL}}` links the API service to the PostgreSQL/Redis services.

Set the Railway service root directory to `/services/api`. `railway.json` uses the Dockerfile and checks `/api/v1/health`. The container start script applies migrations and collects static assets before starting Gunicorn.

## Services

Run the web service with the Dockerfile. Create a second Railway service from the same source/root for Celery and override its start command:

```bash
celery -A config worker --loglevel=INFO
```

A future scheduler service can use:

```bash
celery -A config beat --loglevel=INFO
```

## API

- `GET /api/v1/health` — process liveness
- `GET /api/v1/ready` — PostgreSQL/Redis readiness
- `POST /api/v1/identity/sessions` — role-aware login
- `POST /api/v1/identity/sessions/refresh` — rotate the refresh token and renew the session
- `GET /api/v1/identity/sessions/current` — revalidate and return the current tenant session
- `DELETE /api/v1/identity/sessions/current` — sign out and blacklist a refresh token
- `POST /api/v1/institute-onboarding/registrations` — atomic institute, main branch, and first-admin onboarding
- `GET/PATCH /api/v1/admin/institute` — read or rename the authenticated admin's institute
- `GET/POST /api/v1/admin/branches` — list or create tenant-scoped branches
- `GET/PATCH /api/v1/admin/branches/{branchId}` — read, update, or deactivate a tenant-scoped branch
- `GET /api/schema/` — OpenAPI schema
- `GET /api/docs/` — Swagger UI

Admin login body:

```json
{
  "email": "admin@example.com",
  "password": "your-password",
  "client": "admin-web"
}
```

Authentication is email and password only. CampusOne does not require an SMS/OTP provider.

The web onboarding flow asks only for the institute name, main branch name, administrator name, work email, and password. Institute and branch codes are generated by the server. Public onboarding is rate limited through `INSTITUTE_ONBOARDING_RATE` (default `5/hour`).
Login and refresh are independently rate limited through `IDENTITY_LOGIN_RATE` and `IDENTITY_REFRESH_RATE`. Users with access to multiple institutes must select one of their server-authorized institutes during login; the API never accepts an institute ID as proof of access.

## Create the first institute administrator

Set the password in the environment so it is not exposed in shell history, then run the idempotent bootstrap command:

```bash
export BOOTSTRAP_ADMIN_PASSWORD='<strong-password>'
uv run python manage.py bootstrap_institute \
  --institute-name 'CampusOne Academy' \
  --institute-code 'COA' \
  --branch-name 'Central Campus' \
  --branch-code 'CENTRAL' \
  --admin-email 'owner@example.com'
```

The command can safely be rerun with the same values. Institute administrators remain separate from Django framework superusers and do not receive Django Admin access.
