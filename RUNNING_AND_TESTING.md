# Running and Testing CampusOne Locally

This guide starts the Django API and the Institute Admin web application, verifies both services, and walks through the institute onboarding flow.

## Prerequisites

Install:

- Python 3.11+
- [uv](https://docs.astral.sh/uv/)
- Node.js 20+
- npm
- Optional PostgreSQL and Redis connection details, or Docker for local infrastructure

Run all commands from Git Bash, WSL, or another shell that supports the examples below.

## 1. Configure the API

From the repository root:

```bash
cd services/api
cp .env.example .env
```

Never commit `services/api/.env`. Replace the placeholder secret and service URLs in that file.

### Option A: use Railway PostgreSQL and Redis

Set the following values in `services/api/.env` using the credentials provided by Railway:

```env
DJANGO_ENV=development
DJANGO_DEBUG=true
DJANGO_SECRET_KEY=<long-random-local-secret>
DJANGO_ALLOWED_HOSTS=localhost,127.0.0.1
CORS_ALLOWED_ORIGINS=http://localhost:5173
CSRF_TRUSTED_ORIGINS=http://localhost:5173
DATABASE_URL=<railway-postgresql-url>
DJANGO_USE_SQLITE=false
DATABASE_SSL_REQUIRE=true
REDIS_URL=<railway-redis-url>
CELERY_TASK_ALWAYS_EAGER=false
```

Do not paste real credentials into documentation, source files, terminal screenshots, or commits.

### Option B: use SQLite without external services

SQLite with eager Celery is suitable for quick local development and automated tests. In this mode the readiness endpoint checks SQLite and reports Redis as `skipped`.

Set these values in `services/api/.env`:

```env
DJANGO_ENV=development
DJANGO_DEBUG=true
DJANGO_SECRET_KEY=<long-random-local-secret>
DJANGO_ALLOWED_HOSTS=localhost,127.0.0.1
CORS_ALLOWED_ORIGINS=http://localhost:5173
CSRF_TRUSTED_ORIGINS=http://localhost:5173
DJANGO_USE_SQLITE=true
DATABASE_SSL_REQUIRE=false
REDIS_URL=redis://127.0.0.1:6379/0
CELERY_TASK_ALWAYS_EAGER=true
```

## 2. Install dependencies and prepare the database

In the API directory:

```bash
cd services/api
uv sync --all-groups
uv run python manage.py migrate
uv run python manage.py check
```

Expected final check output:

```text
System check identified no issues (0 silenced).
```

## 3. Start the Django API

Keep this terminal open:

```bash
cd services/api
uv run python manage.py runserver 127.0.0.1:8000 --noreload
```

The API is available at:

- API base: <http://127.0.0.1:8000>
- Swagger UI: <http://127.0.0.1:8000/api/docs/>
- OpenAPI schema: <http://127.0.0.1:8000/api/schema/>
- Liveness: <http://127.0.0.1:8000/api/v1/health>
- Readiness: <http://127.0.0.1:8000/api/v1/ready>

Authenticated API surfaces now include session refresh/current-session/logout and tenant-scoped Institute Admin institute/branch management. Browse their live request and response schemas in Swagger UI.

## 4. Configure and start the Institute Admin web app

Open a second terminal from the repository root:

```bash
cp apps/institute-admin-web/.env.example apps/institute-admin-web/.env
npm install
cd apps/institute-admin-web
npm run dev -- --host localhost --port 5173 --strictPort
```

The web application is available at:

- <http://localhost:5173>

`--strictPort` prevents Vite from silently moving to another port that is not listed in the API CORS configuration.

## 5. Smoke-test both servers

Open a third terminal.

### API liveness

```bash
curl --fail --show-error http://127.0.0.1:8000/api/v1/health
```

Expected response:

```json
{"success":true,"data":{"status":"ok","service":"campusone-api"}}
```

### Database and Redis readiness

```bash
curl --fail --show-error http://127.0.0.1:8000/api/v1/ready
```

A successful response reports the database as `ok` and Redis as either `ok` or `skipped` when eager Celery is enabled. If readiness fails while liveness succeeds, inspect `DATABASE_URL`, `DJANGO_USE_SQLITE`, and `REDIS_URL` in `services/api/.env`.

### Web server

```bash
curl --fail --show-error http://localhost:5173/
```

The response should contain the Vite application HTML. For the real UI check, open <http://localhost:5173> in a browser.

## 6. Test institute onboarding in the browser

1. Open <http://localhost:5173>.
2. Confirm that the unauthenticated page shows only work email and password sign-in fields. CampusOne does not use phone or SMS authentication.
3. Select **Create your institute**.
4. Enter the institute name and main branch name. The branch defaults to **Main Campus** and remains editable.
5. Select **Continue**.
6. Enter the first Institute Admin's full name, work email, password, and password confirmation.
7. Select **Create institute** once.
8. Confirm that the dashboard opens and greets the new administrator by name.

The API creates the institute, main branch, administrator, and institute-wide admin membership in one database transaction. Institute and branch codes are generated by the server.

Use a unique test email for each successful onboarding attempt. Reusing an email should display an inline validation error and must not create another institute.

To test sign-in afterward, use a private browser window or clear the `campusone.session` site-storage entry, then sign in with the same email and password.

## 7. Run automated tests and quality checks

### Backend

```bash
cd services/api
uv run pytest -q -W error
uv run ruff check .
uv run ruff format --check .
uv run python manage.py check
uv run python manage.py makemigrations --check --dry-run
uv run python manage.py spectacular --file schema.yml --validate
```

### Institute Admin web

From the repository root:

```bash
npm run test --workspace @campusone/institute-admin-web
npm run lint --workspace @campusone/institute-admin-web
npm run typecheck --workspace @campusone/institute-admin-web
npm run build --workspace @campusone/institute-admin-web
```

## 8. Optional: test a real Celery worker

Celery runs tasks eagerly in the SQLite setup, so a worker is not required for the onboarding flow. To test Redis-backed background execution, first start Redis if you are not using Railway:

```bash
docker run --rm --name campusone-redis -p 6379:6379 redis:7-alpine
```

Then set these values in `services/api/.env`:

```env
REDIS_URL=redis://127.0.0.1:6379/0
CELERY_TASK_ALWAYS_EAGER=false
```

Then start a worker in another terminal:

```bash
cd services/api
uv run celery -A config worker --pool=solo --loglevel=INFO
```

On Windows, `--pool=solo` avoids multiprocessing compatibility issues. After the worker reports `ready`, verify it from another terminal:

```bash
cd services/api
uv run celery -A config inspect ping --timeout=15
```

Expected output includes `pong` and at least one online node.

## Troubleshooting

### Port 5173 is already in use

Stop the existing frontend process with `Ctrl+C` and restart it. Do not let Vite select 5174 automatically unless you also add `http://localhost:5174` to `CORS_ALLOWED_ORIGINS` and `CSRF_TRUSTED_ORIGINS`.

### Port 8000 is already in use

Stop the existing Django process with `Ctrl+C`, then rerun the API command. Avoid running multiple development servers against the same local port.

### Browser reports a CORS error

Verify that:

- The frontend URL is exactly `http://localhost:5173`.
- `CORS_ALLOWED_ORIGINS` contains `http://localhost:5173`.
- `VITE_API_BASE_URL` is `http://127.0.0.1:8000`.
- Both servers were restarted after environment changes.

### Readiness reports Redis unavailable

Confirm Redis is running and test it directly:

```bash
redis-cli -u "$REDIS_URL" ping
```

Expected output:

```text
PONG
```

### Stop the services

Press `Ctrl+C` in the frontend, API, Celery, and local Redis terminals. The delayed background-process notifications sometimes shown by development tooling do not mean a process is still running; verify the actual terminal/process before starting a duplicate server.
